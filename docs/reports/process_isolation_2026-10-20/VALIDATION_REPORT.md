# CAD 多行程隔離驗證報告

日期：2026-10-20

## 結論

本次概念驗證通過。將 OpenCASCADE 載入、四視圖投影與智慧標註轉檔放進獨立作業系統行程後，同時執行 4 個標註工作仍未造成 Uvicorn API 中斷。

這證明「獨立 Worker 行程 + 有上限的工作佇列」適合進入正式整合階段，而且不需要改寫舊標註引擎。驗證工具只呼叫現有 `SmartAnnotationEngine` 公開介面，未修改 `dimension_engine.py` 或舊 `extractors/`。

正式導入時建議先將 Worker 上限設為 **2**，待加入記憶體監測、逾時、取消、Worker 崩潰重啟及長時間混合模型測試後，再由管理員開放到 3 或 4。測試通過 4 個 Worker 不等於已證明 4 名使用者是所有模型下的永久安全容量。

## 與原架構的差異

先前同一 Uvicorn 行程內進行持續雙工作標註時，原生 CAD／轉檔程式曾讓整個服務行程直接中止，連 `/api/health` 也無法回應。這不是單純把 Semaphore 上限調大能解決的問題。

本次驗證讓每個標註工作由獨立 Python 行程執行。即使日後單一 Worker 遇到原生程式崩潰，Web API 與其他 Worker 仍可存活，排程器可將該工作標記失敗並重建 Worker。

## 建議的最小正式整合

1. 保留目前 API 與前端請求格式，在後端標註入口改成建立工作並回傳 `job_id`。
2. 加入單機持久化佇列；先啟動 2 個獨立 Worker，不使用同一 Python 行程內的 Thread 執行 CAD 工作。
3. 前端輪詢工作狀態，顯示等待順位、目前步驟、完成或失敗原因；重新整理頁面後仍能恢復進度。
4. 管理員可設定的是「Worker 上限」與「佇列上限」，變更前顯示硬體風險提示；初始值為 2。
5. 每名使用者同時間僅允許 1 個執行中工作，但可有 1 個等待中工作，避免重複重新整理製造大量任務。
6. Worker 必須具備逾時、取消、異常退出偵測與自動補建；輸出先寫暫存目錄，成功後再原子搬入使用者工作區。

## 尚未涵蓋

- 超過 4 個 Worker 的破壞性容量上限探索。
- 數十分鐘到數小時的混合模型 soak test。
- Worker 執行期間的尖峰 RSS、CPU、磁碟 I/O 與磁碟空間保護。
- 正式佇列的斷電恢復、重試冪等性與跨機部署。

因此目前可確認的是：4 個隔離 Worker 在兩種代表性模型的短時測試通過，並足以支持以 2 Worker 起步的低風險正式整合；不能宣稱系統已完成最終容量認證。
